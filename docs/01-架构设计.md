# Hiya 服务端架构设计（SpringBoot 重构版）

## 1. 背景：为什么要重构

旧版 Hiya 服务端的技术栈：**Socket 直连 + 自定义 JSON 协议 + 手写 JDBC**。

旧数据流：

```
客户端 --Socket连接--> 服务端接收线程 --JSON--> 分发器(Dispatcher)
      --识别消息类型--> 对应 Service --JDBC--> MySQL
      <--处理结果 JSON，经 Socket 原路返回--
```

重构动机：

- Socket 直连无法被浏览器使用（浏览器只支持 HTTP / WebSocket）；
- 旧版"分发器 + Service"的手工路由，正是 Spring MVC / WebSocket 框架自动完成的事；
- 手写 JDBC 样板代码多（连接管理、预编译、结果集映射），JPA 可自动完成。

## 2. 新架构总览（B-S）

```
Vue3 浏览器端（另一个工作区）
   │  HTTP 请求（REST，URL 带 ?userId=）    WebSocket 长连接（实时推送，?userId= 标识）
   ▼                                        ▼
SpringBoot 服务端（本工作区）
   Controller（REST 入口）                ChatWebSocketHandler（WS 入口）
        │                                        │
        ▼                                        ▼
   Service（业务逻辑，含事务）             SessionManager（在线用户管理）
        │                                        │
        ▼                                        ▼
   Repository（JPA）                       Service（消息落库 + 广播）
        │
        ▼
   MySQL（hiya_db，沿用旧表结构）
```

### 与旧架构的对照

| 旧版 | 新版 | 说明 |
|---|---|---|
| Socket 长连接 | WebSocket（/ws） | 浏览器原生支持，双向实时 |
| 自定义 JSON 消息（cmd 字段路由） | REST（方法+URL 路由）/ WebSocket JSON | 命令从 JSON 字段变成 URL |
| 分发器 Dispatcher | Spring MVC 路由 + WebSocket 处理器 | 框架自动完成 |
| Service | Service 层（接口 + 实现） | 职责相同，可加事务管理 |
| 手写 JDBC | Spring Data JPA | 实体映射表，自动 CRUD |
| （无） | 用户标识 | URL 参数 ?userId=（REST 与 WS 相同；简化设计，不做校验） |

### 一条 REST 请求的完整流转（以登录为例）

```
POST /api/login  {"userName":"hiya","password":"123456"}
  → Tomcat 接收，Spring MVC 路由到 LoginController.login()
  → @Valid 校验参数（失败 → GlobalExceptionHandler 返回 400）
  → UserService.login()：Repository 按用户名查库、比对密码、写一条登录日志
  → 返回 {"code":200,"message":"操作成功","data":{"userId":1,"userName":"hiya"}}
  → 前端记住 userId，之后请求都在 URL 上带 ?userId=1
```

### 一条 WebSocket 消息的完整流转（发消息 → 实时广播）

```
浏览器 new WebSocket('ws://localhost:8080/ws?userId=1')
  → UserIdHandshakeInterceptor 解析 userId 存入握手属性
  → afterConnectionEstablished：SessionManager.add(userId, session)，用户上线
  → 发送消息走 REST：POST /api/chat/3/messages（URL 带 ?userId=1）
  → ChatService 落库 + 查会话成员 → SessionManager.pushToUsers(成员, "BROADCAST_MESSAGE", 消息)
  → 会话内在线的浏览器 onmessage 收到 {"type":"BROADCAST_MESSAGE","data":{...}}
```

## 3. 分层职责（为什么这样分层）

| 层 | 包 | 职责 | 禁止做的事 |
|---|---|---|---|
| 表现层 | controller | 收参数、调 Service、包 Result | 写业务逻辑、碰数据库 |
| 业务层 | service | 业务规则、事务、跨表操作 | 出现 HTTP 概念 |
| 数据层 | repository | 单表 CRUD（JPA 自动生成） | 写业务规则 |
| 实体层 | entity | 表结构映射 | 承载请求参数（用 dto） |
| 通用层 | common | Result、状态码、异常、全局处理 | 依赖具体业务 |
| 配置层 | config | CORS、WebSocket 注册 | — |
| 实时层 | ws | 长连接管理、消息收发推送 | 复杂业务逻辑 |

分层收益：单一职责、可单独测试、可替换实现（如换数据库只动 repository）。

## 4. 五个入口（Controller）与接口一览

项目按"三大业务 + 首页 + 实时通道"组织，共 5 个 Controller：

| # | 入口 | Controller | 负责的业务 |
|---|---|---|---|
| 1 | `/` | HomeController | 首页：服务状态 + 接口清单（浏览器直接打开就能看，确认服务是否在跑） |
| 2 | `/api/register` | RegisterController | 注册 |
| 3 | `/api/login`、`/api/me`、`/api/info/{id}` | LoginController | 登录 + 当前用户 + 用户资料 |
| 4 | `/api/chat/**` | ChatController | 聊天：会话列表、私聊、成员、发消息、聊天记录 |
| 5 | `/api/friend/**` | FriendController | 好友：列表、在线、请求、同意/拒绝、删除 |
| — | `/ws?userId=` | ChatWebSocketHandler | WebSocket 实时通道（服务器主动推送，不占 Controller） |

### 关键概念：Controller / Service / Repository 的数量**不需要**一一对应

| 层 | 数量 | 划分依据 | 例子 |
|---|---|---|---|
| Controller | 5 | 按**入口**划分（一个入口一个类） | RegisterController、LoginController |
| Service | 3 | 按**业务模块**划分 | UserService（登录注册）、ChatService（聊天）、FriendService（好友） |
| Repository | 7 | 按**数据库表**划分 | 7 张表 → 7 个 Repository |

为什么不对应？

- `RegisterController` 和 `LoginController` 都用同一个 `UserService`——它们操作的是同一块业务（用户账号），
  拆成两个 Service 只会让 `register`/`login` 各自重复一份用户查询代码；
- `ChatService`（聊天）同时用到 `ChatRepository`（会话表）、`ChatMemberRepository`（成员表）、
  `MessageRepository`（消息表）——**一次业务往往要碰多张表**；
- 所以：**Controller 看"入口"，Service 看"业务"，Repository 看"表"**，各自按最自然的边界切分即可。

> 一句话记忆：**入口数 ≠ 业务数 ≠ 表数**。硬凑成 1:1 反而会让代码难维护。

请求示例（登录，无需任何身份信息）：

```
POST http://localhost:8080/api/login
Content-Type: application/json

{"userName":"hiya","password":"123456"}
```

响应示例：

```json
{"code":200,"message":"操作成功","data":{"userId":1,"userName":"hiya"}}
```

之后请求业务接口时带上标识身份的头：

```
GET http://localhost:8080/api/friend/list
?userId=1
```

> 全部接口已用真实旧库数据 + WebSocket 客户端端到端验证（见 README「当前进度」）。

## 5. WebSocket 消息协议（当前）

| 方向 | 消息 | 说明 |
|---|---|---|
| 客户端→服务器 | {"type":"ping"} | 心跳，保活连接 |
| 服务器→客户端 | {"type":"pong"} | 心跳应答 |
| 服务器→客户端 | {"type":"BROADCAST_MESSAGE","data":{...}} | 会话内有新消息（发消息后广播） |
| 服务器→客户端 | {"type":"FRIEND_REQUEST_NOTIFY","data":{...}} | 有人请求加你为好友 |
| 服务器→客户端 | {"type":"ADD_FRIEND_RESULT","data":{...}} | 你的好友请求被同意/拒绝 |

业务上行（发消息、加好友等）全部走 REST，WebSocket 只负责"服务器主动推"。

## 5.1 学习笔记：Spring Boot 4 的 Jackson 3 坑

网上绝大多数教程基于 Spring Boot 2/3（Jackson 2），直接照抄会踩坑：

- **包名变了**：Jackson 3 把 databind/core 从 `com.fasterxml.jackson.databind` 迁到了
  `tools.jackson.databind`（`ObjectMapper`、`JsonNode` 等）。注入 ObjectMapper 要用
  `tools.jackson.databind.ObjectMapper`。
- **注解没变**：`@JsonProperty` 等注解仍保留在 `com.fasterxml.jackson.annotation`，
  不要改成 `tools.jackson.annotation`（该包不存在）。
- **方法名变了**：`JsonNode.asText()` 在 Jackson 3 已废弃，改用 `asString()`。
- （历史）项目曾用 JWT，当时为避免"Jackson 2/3 两套并存"而选用 jjwt-gson；
  现已按需求移除 JWT，该依赖也已移除。
